# 🌿 G6 — Production Hardening: Full Implementation Plan

---

## The Nature of This Phase

G6 is the **final gate** before HerbChain goes live. Unlike G1–G5 which built features and migrated screens, G6 is about **trust, resilience, and readiness**. A single security vulnerability, a missing test, or a performance bottleneck can undermine the entire platform.

This phase has three distinct tracks running in parallel:

```
Track A: SECURITY        → Hardening, authentication, audit
Track B: QUALITY         → E2E tests, integration tests, load tests
Track C: POLISH          → Settings, onboarding, cleanup, extras
```

---

## Implementation Order

Security and testing are P0 — they gate the production launch. Polish and cleanup follow.

```
Step 1  → Security Hardening (P0 — gates everything)
Step 2  → E2E Regression Tests (P0 — validates full chain)
Step 3  → Cross-Role Integration Tests (P1 — validates interactions)
Step 4  → Performance & Load Tests (P1 — validates scalability)
Step 5  → Settings Across All Roles (P1 — user-facing completeness)
Step 6  → Old Backend Removal (P1 — final cleanup)

Step 8  → Role Switcher (P2 — multi-role support)
Step 9  → AI Flow Polish (P2 — identification quality)
Step 10 → Dead Code Cleanup (P2 — codebase hygiene)
Step 11 → Farmer Extras (P2 — adoption boosters)
Step 12 → API Versioning & Migration Guide (P2 — documentation)
Step 13 → Production Readiness Review (final gate)
```

## STEP 1: Security Hardening (Gap 6.5)

**What:** A comprehensive security overhaul covering authentication, session management, data protection, and access control. This is the single most important step in G6 because HerbChain handles sensitive supply chain data, government regulatory information, and farmer personal details.

**Why first:** No other G6 step matters if the platform can be breached. Security is the production gate.

### 1A. Security Threat Model for HerbChain

| Threat | Risk Level | Attack Vector | Mitigation |
|---|---|---|---|
| **Unauthorized ownership transfer** | Critical | Attacker scans QR and transfers batch they don't own | Multi-factor transfer validation (QR + role + authorization + GPS) |
| **QR spoofing** | Critical | Attacker generates fake QR codes | Server-side token validation, single-use QR tokens, blockchain anchoring |
| **Session hijacking** | High | Stolen JWT token used from different device | Device binding, short-lived tokens, refresh rotation, biometric re-auth |
| **Data tampering** | High | Attacker modifies batch/lab data in transit | HTTPS enforcement, request signing, blockchain anchoring of critical events |
| **Role escalation** | High | Transporter accesses admin functions | Strict RBAC enforcement on every API endpoint, server-side only |
| **Farmer data exposure** | Medium | Consumer API leaks farmer PII | Consumer-safe projection (already built in G2), API-level field filtering |
| **Replay attacks** | Medium | Attacker replays old transfer requests | Timestamp validation, nonce tokens, idempotency keys |
| **Denial of service** | Medium | Flooding API with requests | Rate limiting, request throttling, CAPTCHA on auth endpoints |
| **Offline data theft** | Medium | Stolen device exposes cached offline data | Encrypted local storage, biometric lock on app |
| **Supply chain fraud** | Critical | Fake lab certificate or fake batch | Blockchain verification, document hash checking, cross-reference validation |

### 1B. Technical Approach

| Item | Choice | Reason |
|---|---|---|
| Authentication | JWT + Refresh Token rotation | Industry standard, supports offline mode |
| Biometric | `expo-local-authentication` | Fingerprint/Face ID on supported devices |
| PIN fallback | Custom 6-digit PIN screen | For devices without biometric hardware |
| Session management | Server-side session store + device binding | Prevents token reuse across devices |
| Data encryption | AES-256 for local storage, TLS 1.3 for transit | Protects offline data and API calls |
| Rate limiting | `express-rate-limit` on backend | Prevents API abuse |
| Input validation | `zod` schemas on all API inputs | Prevents injection attacks |
| CORS | Strict origin whitelist | Prevents unauthorized web access |
| Audit logging | Every auth event logged to blockchain | Immutable security audit trail |

### 1C. Implementation Tasks

**Task 1.1 — Implement biometric/PIN authentication**
```
Location: App/screens/auth/BiometricLockScreen.js

Purpose:
- When user opens the app after being away for >5 minutes
- When user attempts a sensitive action (transfer, certify, recall)
- When user accesses admin functions

Flow:
1. App detects user returning from background (>5 min)
2. Shows lock screen:
   ┌─────────────────────────────────────┐
   │  🔒 HerbChain Locked                │
   │                                     │
   │  [👆 Use Fingerprint]               │
   │  [👁️ Use Face ID]                   │
   │  [🔢 Use PIN]                        │
   │                                     │
   │  Attempt 1 of 5                     │
   └─────────────────────────────────────┘
3. On biometric success → unlock app
4. On biometric failure → fallback to PIN
5. On 5 failed attempts → lock app for 15 minutes
6. On 10 failed attempts → require re-login with credentials

Configuration (in Settings):
- Enable/disable biometric lock
- Set lock timeout (1 min, 5 min, 15 min, never)
- Change PIN
- Require biometric for transfers (toggle)
```

**Task 1.2 — Implement session management**
```
Location: Backend middleware + App/contexts/AuthContext.js

Backend session rules:
- JWT access token: 15-minute expiry
- Refresh token: 7-day expiry, single-use rotation
- Device binding: token tied to device fingerprint (device ID + OS + app version)
- Concurrent sessions: max 2 devices per user (mobile + web)
- Session revocation: admin can force-logout any user
- Inactivity timeout: 30 minutes of no API calls → session invalidated

Frontend session handling:
- Silent refresh: auto-refresh token 1 minute before expiry
- Refresh failure → redirect to login
- Device mismatch detected → force re-authentication
- Network error during refresh → queue and retry (offline support)
```

**Task 1.3 — Implement RBAC enforcement audit**
```
Location: Backend middleware (extend existing Auth/RBAC from Phase 1)

Audit every API endpoint:
- Verify that each endpoint checks the user's role
- Verify that each endpoint checks the user's permissions within that role
- Verify that cross-role access is impossible:
  - Farmer cannot call Lab endpoints
  - Transporter cannot call Manufacturer endpoints
  - Consumer cannot call any write endpoints
  - Admin can call all read endpoints but only specific write endpoints

Test matrix:
  For each of the ~140 API endpoints:
  - Call with Farmer token → should succeed or 403
  - Call with Transporter token → should succeed or 403
  - Call with Lab token → should succeed or 403
  - Call with Manufacturer token → should succeed or 403
  - Call with Consumer token → should succeed or 403
  - Call with Admin token → should succeed or 403
  - Call with no token → should 401
  - Call with expired token → should 401
  - Call with tampered token → should 401
```

**Task 1.4 — Implement data encryption for offline storage**
```
Location: App/stores/OfflineQueueStore.js (extend) + App/utils/encryption.js

Requirements:
- All offline queue data encrypted with AES-256
- Encryption key derived from user PIN/biometric
- Key stored in device secure enclave (Keychain on iOS, Keystore on Android)
- On app unlock → decrypt offline queue → sync → re-encrypt
- On failed biometric → offline data remains encrypted and inaccessible
- On app uninstall → encryption keys destroyed
```

**Task 1.5 — Implement API security headers and rate limiting**
```
Location: Backend middleware

Security headers (all responses):
- Strict-Transport-Security: max-age=31536000; includeSubDomains
- X-Content-Type-Options: nosniff
- X-Frame-Options: DENY
- X-XSS-Protection: 1; mode=block
- Content-Security-Policy: strict policy
- Referrer-Policy: strict-origin-when-cross-origin

Rate limiting:
- Auth endpoints: 5 requests per minute per IP
- API endpoints: 100 requests per minute per user
- Upload endpoints: 10 requests per minute per user
- Verify endpoints (consumer): 30 requests per minute per IP
- Admin endpoints: 200 requests per minute per admin

DDoS protection:
- Request size limit: 10MB
- JSON depth limit: 5 levels
- Slowloris protection: 30-second request timeout
```

**Task 1.6 — Implement security audit logging**
```
Location: Backend middleware + Blockchain integration

Every security-relevant event logged:
- Login success/failure (with IP, device, timestamp)
- Token refresh
- Session revocation
- Role change
- Permission denied (403)
- Biometric failure
- PIN failure
- Account lockout
- Password change
- Data export
- Admin action (recall, suspend, compliance)

Critical events anchored to blockchain:
- Account lockout
- Admin recall trigger
- Compliance violation resolution
- User suspension
- Certificate revocation
```

```
Scope:

4. Lab result tampering
5. Consumer data exposure through API

Deliverable:

| CI/CD | GitHub Actions | Automated on every PR and nightly |

## STEP 3: Cross-Role Integration Tests (Gap 6.7)

**What:** Tests that specifically validate the interactions between different roles — the handoff points where ownership transfers, notifications cross role boundaries, and data flows between systems.

**Why third:** E2E tests (Step 2) validate the happy path. Integration tests validate the **boundaries** between roles, which is where most real-world bugs occur.

### 3A. Implementation Tasks

**Task 3.1 — Farmer ↔ Transporter integration tests**
```
Scenarios:
- Farmer creates batch → Transporter sees it in pickup queue
- Transporter scans farmer QR → Farmer gets "picked up" notification
- Transporter confirms pickup → Farmer's batch status changes to IN_TRANSIT
- Farmer tries to transfer already-picked-up batch → rejected
- Transporter tries to scan batch not assigned to them → rejected
- Multiple transporters assigned to same pickup → only first scan succeeds
- Farmer cancels transfer request → Transporter's assignment removed
```

**Task 3.2 — Transporter ↔ Lab integration tests**
```
Scenarios:
- Transporter delivers to lab → Lab sees batch in receive queue
- Lab scans transporter QR → Transporter gets "delivered" notification
- Lab rejects batch → Transporter gets "rejected" notification
- Lab requests re-delivery → New transporter assignment created
- Transporter delivers wrong batch → Lab scan rejects mismatch
- POD upload by transporter → Lab can view POD before accepting
```

**Task 3.3 — Lab ↔ Manufacturer integration tests**
```
Scenarios:
- Lab certifies batch → Manufacturer sees it in marketplace
- Lab rejects batch → Manufacturer cannot see it
- Manufacturer requests batch → Lab gets release request
- Lab releases batch → Transporter assigned for pickup
- Lab revokes certificate after manufacturer receives → compliance alert
- Manufacturer tries to use uncertified batch → blocked
```

**Task 3.4 — Manufacturer ↔ Consumer integration tests**
```
Scenarios:
- Manufacturer creates product → Consumer can scan product QR
- Product lineage shows all input batches → Consumer sees all origins
- Manufacturer recalls product → Consumer sees recall alert

**Task 3.5 — Admin ↔ All Roles integration tests**
```
Scenarios:
- Admin suspends farmer → Farmer cannot login
- Admin suspends transporter → Active shipments flagged
- Admin triggers recall → All affected roles notified
- Admin resolves compliance violation → Related role notified
- Admin views user activity → sees all role actions
- Admin exports report → data matches all role views
```

## STEP 4: Performance & Load Tests (Gap 6.8)

**What:** Tests that verify HerbChain performs acceptably under realistic and peak loads — including API response times, database query performance, blockchain anchoring latency, and mobile app rendering speed.

**Why fourth:** The platform may work perfectly with 10 users but collapse with 10,000. Performance testing catches scalability issues before they hit production.

### 4A. Performance Targets

| Metric | Target | Critical Threshold |
|---|---|---|
| API response time (average) | < 500ms | > 2s = fail |
| API response time (P95) | < 1s | > 5s = fail |
| QR scan → transfer complete | < 3s | > 10s = fail |
| Consumer passport load | < 2s (4G) | > 5s = fail |
| Consumer passport load | < 4s (3G) | > 8s = fail |
| Dashboard load (admin web) | < 3s | > 8s = fail |
| Report generation (P16) | < 5s | > 15s = fail |
| Blockchain anchor time | < 30s | > 2min = fail |
| Mobile app cold start | < 3s | > 5s = fail |
| Offline sync (100 items) | < 30s | > 2min = fail |
| Concurrent users supported | 1,000 | < 500 = fail |
| Database query (complex) | < 1s | > 5s = fail |
