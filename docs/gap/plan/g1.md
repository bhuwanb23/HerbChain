## STEP 1: Sync Status Indicator (Gap 1.4)

**What:** A global banner/icon visible on every screen that shows connectivity state.
**Why first:** Every other G1 component depends on knowing whether the device is online or offline.

### 1A. Technical Approach

| Item | Choice | Reason |
|---|---|---|
| Network detection | `@react-native-community/netinfo` | Industry standard, works on iOS + Android |
| State management | React Context (`NetworkContext`) | Lightweight, no extra library needed |
| Visual | Top banner bar | Non-intrusive, always visible |

### 1B. Implementation Tasks

**Task 1.1 — Install dependency**
```bash
npx expo install @react-native-community/netinfo
```

**Task 1.2 — Create `NetworkContext.js`**
```
Location: App/contexts/NetworkContext.js

Responsibilities:
- Subscribe to NetInfo.addEventListener on mount
- Track: isConnected (bool), connectionType (wifi/cellular/none)
- Expose: { isOnline, connectionType, lastChecked }
- Debounce state changes (avoid flickering on weak signals)
```

**Task 1.3 — Create `SyncStatusBar` component**
```
Location: App/components/SyncStatusBar.js

States:
┌─────────────────────────────────────────────────┐
│ 🟢 Online — All changes synced                  │  ← green, subtle

│ 🟠 Sync Error — Tap to retry                    │  ← orange, tappable
└─────────────────────────────────────────────────┘

Props:
- pendingCount: number (from offline queue)
- syncState: 'idle' | 'syncing' | 'error'
- onRetry: function
```

**Task 1.4 — Integrate into root layout**
```
Location: App/navigation/AppNavigator.js (or root layout)

Wrap the entire app:

  <SyncStatusBar />
  <Navigation />
</NetworkProvider>
```

## STEP 2: Transporter QR Scanner (Gap 1.1)

**What:** Camera-based QR scanner that reads a batch QR token, validates it against the backend, executes ownership transfer, and displays the new QR.
**Why critical:** This is the single most important missing screen. Without it, transporters cannot participate in the dynamic ownership chain.

### 2A. Technical Approach

| Item | Choice | Reason |
|---|---|---|
| Camera/Scanner | `expo-camera` (Expo SDK 51+) | Built-in barcode scanning, no native config |
| QR Parsing | Extract token string from QR data | QR contains only a secure token, not full data |
| API | `TransfersAPI.initiate()` + `TransfersAPI.confirm()` | Two-step transfer for safety |
| New QR Display | `react-native-qrcode-svg` | Generate new QR after transfer |

### 2B. Implementation Tasks

**Task 2.1 — Install dependencies**
```bash
npx expo install expo-camera
npm install react-native-qrcode-svg react-native-svg
```

**Task 2.2 — Create `ScannerScreen` (main scanner)**
```
Location: App/screens/transporter/ScannerScreen.js

Flow:
1. Request camera permission (expo-camera)
2. Open camera view with scan area overlay
3. On QR detected → extract token string
4. Pause scanner (prevent duplicate scans)
5. Call API: POST /api/transfers/validate-qr
   Body: { qrToken, transporterId, gpsLocation }
6. Handle response:
   - VALID → Show confirmation screen (Task 2.3)
   - INACTIVE_QR → Error: "This QR has been deactivated"
   - WRONG_OWNER → Error: "You are not the authorized receiver"
   - BATCH_MISMATCH → Error: "QR does not match expected batch"
   - UNAUTHORIZED → Error: "Transfer not authorized"
7. After confirmation → Call API: POST /api/transfers/confirm
8. On success → Show new QR screen (Task 2.4)
```

## STEP 4: Offline Sync UI + Manual Trigger (Gaps 1.3, 1.5)

**What:** A screen showing queued offline transactions with sync status, plus a manual sync button.
**Why:** Farmers and transporters work in low-connectivity areas. They need to see what's pending and force a sync.

### 4A. Technical Approach

| Item | Choice | Reason |
|---|---|---|
| Local storage | `expo-sqlite` or `AsyncStorage` | Backend Phase 14 already defines the sync schema |
| Queue model | Array of `{ id, type, payload, status, timestamp, retryCount }` | Matches backend offline sync API |
| Sync trigger | Button + auto-sync on reconnect | Both manual and automatic |

### 4B. Implementation Tasks

**Task 4.1 — Create `OfflineQueueStore`**
```
Location: App/stores/OfflineQueueStore.js

Data structure:
{
  id: 'local-uuid',
  type: 'BATCH_CREATE' | 'TRANSFER_CONFIRM' | 'GPS_PING' | 'POD_UPLOAD',
  payload: { ... },        // The API request body
  status: 'pending' | 'syncing' | 'synced' | 'failed',
  timestamp: ISO string,
  retryCount: number,
  error: string | null
}

Methods:
- enqueue(type, payload)
- markSyncing(id)
- markSynced(id)
- markFailed(id, error)
- getPending()
- clearSynced()
```

**Task 4.2 — Create `OfflineQueueScreen`**
```

Layout:

```

**Task 4.3 — Create `ManualSyncButton` component**
```
Location: App/components/ManualSyncButton.js

Behavior:
1. Tap → Check network (from NetworkContext)
2. If offline → Show toast "No internet connection"
3. If online → 
   a. Set syncState = 'syncing'
   b. Fetch all pending items from OfflineQueueStore
   c. For each item:
      - markSyncing(id)
      - POST to appropriate API endpoint
      - On success: markSynced(id)
      - On failure: markFailed(id, error)
   d. Set syncState = 'idle' or 'error'
4. Show progress: "Syncing 2/5..."
5. Show result: "3 synced, 2 failed"
```

**Task 4.4 — Auto-sync on reconnect**
```
Location: App/contexts/NetworkContext.js (extend)

Add listener:
- When isOnline changes from false → true
- Wait 5 seconds (stability check)
- Auto-trigger sync if pendingCount > 0
- Update SyncStatusBar to "Syncing..."
```

**Task 4.5 — Wire into Farmer and Transporter profiles**
```
Farmer Profile → Add "Offline Queue" menu item
Transporter Profile → Add "Offline Queue" menu item
```

## STEP 5: Sync Conflict Resolution (Gap 1.6)

**What:** A screen that appears when an offline transaction conflicts with the current server state (e.g., someone else already transferred the batch).
**Why:** Rare but critical — prevents data corruption in edge cases.

### 5A. Technical Approach

| Item | Choice | Reason |
|---|---|---|
| Conflict detection | Server returns `409 CONFLICT` on sync | Backend Phase 14 handles this |
| Resolution strategy | Server-wins by default + user notification | Safest for supply chain integrity |
| UI | Modal overlay on sync | Non-blocking, clear |

### 5B. Implementation Tasks

**Task 5.1 — Create `ConflictResolutionModal`**
```
Location: App/components/ConflictResolutionModal.js

Layout:
┌─────────────────────────────────────┐
│  ⚠️ Sync Conflict Detected          │
│                                     │
│  Your offline action conflicts with │
│  the current server state.          │
│                                     │
│  Your Action:                       │
│  Transfer HERB-001 to Transporter-07│
│  Time: 2:30 PM (offline)            │
│                                     │
│  Server State:                      │
│  HERB-001 already transferred to    │
│  Transporter-03 at 2:15 PM          │
│                                     │
│  The server version will be kept    │
│  to maintain chain integrity.       │
│                                     │
│  [View Server Version]  [Dismiss]   │
└─────────────────────────────────────┘
```

**Task 5.2 — Handle conflict in sync flow**
```
Location: App/stores/OfflineQueueStore.js (extend sync method)

On 409 response:
1. Mark item as 'conflict' (new status)
2. Store server state from response
3. Show ConflictResolutionModal
4. On dismiss → mark item as 'resolved' (server-wins)
5. Log conflict for admin review
```

**Task 5.3 — Admin conflict log**
```
Location: Extend AdminAPI

- Conflicts are logged to backend as COMPLIANCE events
- Admin can review in CompliancePage (G3 will build the UI)
```
