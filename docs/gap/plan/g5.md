# 🌿 G5 — Legacy Unification: Full Implementation Plan

---

## Nature of This Phase

G5 is fundamentally different from G1–G4. Those phases built **new** screens and features. G5 is a **systematic migration** — taking 15 screens that already exist in the codebase but call dead or deprecated APIs, and rewiring them to the new Prisma-backed backend.

The risk in G5 is not "can we build it?" but **"can we migrate without breaking what already works?"** Every screen must be tested against the new data models, and the old API references must be surgically removed.

---

## Migration Methodology (Apply to Every Screen)

Every screen in G5 follows the same 6-step migration pattern:

```
Step A: Audit
  → Identify all old API calls in the screen
  → Map each old endpoint to its new equivalent
  → Identify data model differences (field names, types, nesting)

Step B: Isolate
  → Create a new API service file for the screen (if not exists)
  → Define the new data types/interfaces matching Prisma schema
  → Do NOT touch the UI yet

Step C: Rewire Data Layer
  → Replace old API calls with new API calls
  → Add data transformation layer where field names differ
  → Handle new response formats (pagination, error codes)

Step D: Update UI Bindings
  → Update screen components to use new data shapes
  → Fix any broken field references (e.g., old: batch.herb_name → new: batch.herb.species)
  → Update loading/error/empty states

Step E: Regression Test
  → Test the screen in isolation
  → Test cross-screen navigation (does the migrated screen break adjacent screens?)
  → Compare data output with old screen (same numbers, same lists)

Step F: Deprecate Old Reference
  → Remove old API import
  → Remove old data type definitions
  → Add comment: "Migrated to new API — G5"
```

---

## Implementation Order

Group by role to minimize context-switching and maximize shared API reuse:

```
Step 1 → Farmer Screens (5.1–5.4) — 4 screens, heaviest migration
Step 2 → Lab Screens (5.5–5.7) — 3 screens, includes one partial rebuild
Step 3 → Manufacturer Screens (5.8–5.9, 5.15) — 3 screens
Step 4 → Admin Mobile Verification (5.10–5.12) — 3 screens, verify G3 work
Step 5 → Consumer + Transporter (5.13–5.14) — 2 screens, one new build
Step 6 → Full Codebase Audit — grep, cleanup, deprecation
Step 7 → End-to-End Regression Test
```

## STEP 1: Farmer Screens Migration (Gaps 5.1–5.4)

**What:** Migrate 4 farmer screens from old API to new BatchesAPI, CatalogueAPI, and AuthAPI.

**Why first:** Farmer screens have the most old-flow references and the most complex data model changes (the new backend separates herbs, batches, and catalogue items into distinct Prisma models).

### 1A. Screen-by-Screen Migration Map

#### Screen 5.1: HerbList / HerbRegister / HerbDetails

| Aspect | Old Flow | New Flow |
|---|---|---|
| **HerbList** | `GET /old/herbs` → flat list of herb records | `GET /api/batches/mine` → batches grouped by herb species, with catalogue enrichment |
| **HerbRegister** | `POST /old/herbs` → creates herb + batch in one call | `POST /api/batches` → creates batch; herb species comes from CatalogueAPI |
| **HerbDetails** | `GET /old/herbs/:id` → single herb record | `GET /api/batches/:id` → batch detail + linked catalogue entry + transfer history |
| **Data model shift** | Herb and Batch were one entity | Herb is a catalogue entry; Batch is a separate entity linked to a catalogue herb |
| **Key field changes** | `herb.name` → `batch.herb.species` | `herb.origin` → `batch.harvestLocation` |
| | `herb.quantity` → `batch.weight` | `herb.status` → `batch.status` (different enum values) |
| | `herb.date` → `batch.harvestDate` | `herb.farmer_id` → `batch.farmerId` (camelCase) |

**Migration Tasks:**

**Task 1.1 — Audit HerbList**
```
Identify all old API calls:
- GET /old/herbs → replace with BatchesAPI.mine()
- GET /old/herbs/search → replace with BatchesAPI.mine({ search: query })
- GET /old/herbs/filter → replace with BatchesAPI.mine({ status, species })

Data transformation needed:
- Old: flat herb list → New: batch list with herb species from catalogue
- Old: herb.image_url → New: batch.images[0] (array of images)
- Old: herb.ai_confidence → New: batch.identification.confidence
- Group batches by species for display (mimic old herb-centric view)
```

**Task 1.2 — Audit HerbRegister**
```
Identify all old API calls:
- POST /old/herbs → replace with BatchesAPI.create()

Data transformation needed:
- Old: single form submission → New: two-step (identify + register)
- Old: herb fields inline → New: batch fields + catalogue reference
- Add catalogue species selection (dropdown from CatalogueAPI)
- Add AI identification flow (SmartRegister already exists — merge logic)
- Map form fields to new Prisma schema:
  species, harvestDate, weight, cultivationType,
  harvestLocation (GPS), farmLocation, qualityNotes, images[]
```

**Task 1.3 — Audit HerbDetails**
