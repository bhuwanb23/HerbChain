G3 has a mix of critical migrations and new builds. Order by regulatory impact and dependency chain:

```
Step 1 → Alerts & Recall (P0 — safety-critical, feeds G2 consumer alerts)
Step 2 → Reports & Analytics (P1 — largest migration, P16 backend ready)
Step 3 → Compliance Monitoring (P1 — core regulatory function)
Step 4 → Blockchain Audit (P1 — new page, unique HerbChain capability)

Step 7 → Support & Disputes (P2 — stakeholder issue management)
Step 8 → Incentives (P2 — farmer programs)
Step 9 → Full Admin Integration Test
```

## STEP 1: Alerts & Recall Migration (Gap 3.3)

**What:** The admin's ability to trigger product/batch recalls, view recall impact across the supply chain, and push notifications to all affected parties — including consumers who scanned the product.

**Why first:** This is the only P0 item in G3. It's safety-critical, and G2's consumer recall alert view depends on the admin being able to trigger recalls from this page.

### 1A. Current State vs Target State

| Aspect | Current (Old API) | Target (New API) |
|---|---|---|
| Data source | Legacy recall endpoints | P16 Analytics + Notifications API |
| Recall trigger | Manual flag in old DB | `AdminAPI.recalls.trigger()` with impact analysis |
| Impact analysis | None | Full supply chain traversal — which batches, which products, which consumers |
| Consumer notification | None | Push to all previous scanners via NotificationsAPI |
| Status tracking | Basic | Full lifecycle: Draft → Active → Resolved |
| Audit trail | None | Every recall action logged to blockchain |

### 1B. Technical Approach

| Item | Choice | Reason |
|---|---|---|
| Recall scope | Product-level or Batch-level | Admin can recall a single batch or an entire product line |
| Impact engine | Backend graph traversal | Walks the parent-child lineage to find all affected products/batches |
| Notification cascade | NotificationsAPI + Push | Alerts manufacturers, transporters, labs, and consumers simultaneously |
| Recall lifecycle | State machine: DRAFT → ACTIVE → RESOLVED → ARCHIVED | Prevents accidental activation, allows review before going live |
| Blockchain anchor | Recall events written to chain | Immutable proof that recall was issued at a specific time |

  - Search by Product ID, Batch ID, or Product Name
  - Select from results

Step 2: Define Recall Details
  - Severity: [Critical] [High] [Medium] [Low]
  - Reason: Dropdown + free text
    - Contamination
    - Mislabeling
    - Failed Lab Test (post-market)
    - Regulatory Directive
    - Other
  - Effective Date: Immediate or Scheduled
  - Instructions for consumers
  - Manufacturer contact information

Step 3: Impact Preview
  - Backend runs impact analysis BEFORE activation
  - Shows:

Step 4: Activate
  - Admin confirms activation
  - System:
    1. Sets recall status = ACTIVE
    2. Flags all affected products/batches in database
    3. Triggers notifications to all stakeholders
    4. Sends push to consumers who scanned affected products
    5. Anchors recall event to blockchain
    6. Updates consumer passport views (G2 Step 6)
```

## STEP 2: Reports & Analytics Migration (Gap 3.1)

**What:** Migrate the admin reports page from old API to the new P16 analytics backend, which covers 10 analytics domains.

**Why second:** This is the largest migration in G3. P16 backend is already complete — the data exists, it just needs a new frontend.

### 2A. Current State vs Target State

| Aspect | Current (Old API) | Target (P16 Analytics) |
|---|---|---|
| Data source | Legacy aggregation queries | P16 Analytics API (10 domains) |
| Refresh | Static, page-load only | Real-time with auto-refresh |
| Domains | 3-4 basic charts | 10 comprehensive domains |
| Filters | None | Date range, region, role, status |
| Export | None | CSV, PDF |
| Drill-down | None | Click chart → see underlying data |

### 2B. P16 Analytics Domains

The backend already supports these 10 domains. Each needs a visualization:

| # | Domain | Key Metrics | Chart Type |
|---|---|---|---|
| 1 | **Supply Chain Volume** | Total batches, transfers, shipments over time | Line chart |
| 2 | **Farmer Analytics** | Registered farmers, batches per farmer, regional distribution | Bar chart + Map |
| 3 | **Transport Analytics** | Active shipments, average transit time, delivery success rate | KPI cards + Line |
| 4 | **Lab Analytics** | Tests conducted, pass/fail rate, average turnaround time | Donut + Bar |
| 5 | **Manufacturing Analytics** | Products created, batches consumed, production volume | Stacked bar |
| 6 | **Quality Analytics** | Certification rate, rejection reasons, quality trends | Heatmap + Line |
| 7 | **Compliance Analytics** | Violations, unauthorized transfers, expired certs | Alert table + Trend |
| 8 | **Blockchain Analytics** | Events anchored, chain health, sync status | KPI cards |
| 9 | **Consumer Analytics** | Scans, verifications, share rate, recall views | Funnel + Line |
| 10 | **Geographic Analytics** | Regional distribution of farms, labs, manufacturers | Interactive map |

### 2C. Technical Approach

| Item | Choice | Reason |
|---|---|---|
| Charting library | `recharts` (React) | Lightweight, customizable, works well with Vite |
| Map visualization | `react-leaflet` | Open-source, no API key needed |
| Data fetching | React Query (`@tanstack/react-query`) | Caching, auto-refresh, loading states |
| Filters | URL query parameters | Shareable, bookmarkable report views |
| Export | `jspdf` + `html2canvas` for PDF; `papaparse` for CSV | Client-side generation, no backend load |
| Auto-refresh | 60-second polling interval | Configurable per domain |

**Why third:** After recalls and analytics, compliance is the most critical regulatory function.

| Notifications | None | Real-time alerts to admin + relevant stakeholders |

| 4 | **Chain Break** | Missing ownership link in custody chain | High |
| 5 | **GPS Anomaly** | Shipment location deviates from expected route | Medium |
| 6 | **QR Tampering** | Deactivated QR scanned again | Critical |
| 7 | **Volume Mismatch** | Batch weight changes significantly during transfer | High |
| 8 | **Duplicate Registration** | Same herb batch registered twice | Medium |

## STEP 4: Blockchain Audit Page (Gap 3.7)

**What:** A new page that lets AYUSH admins explore all blockchain-anchored events, verify transaction hashes, and confirm that the on-chain record matches the database.

**Why fourth:** This is HerbChain's unique differentiator. No other AYUSH system offers cryptographic proof of supply chain events.

### 4A. Technical Approach

| Item | Choice | Reason |
|---|---|---|
| Data source | Blockchain Phase 12 events + operational DB | Cross-reference on-chain vs off-chain |
| Event types | BATCH_CREATED, OWNERSHIP_TRANSFERRED, LAB_CERTIFIED, BATCH_REJECTED, PRODUCT_CREATED, BATCH_LINKED, RECALL_TRIGGERED, RECALL_RESOLVED | All critical events from smart contracts |
| Verification | Hash comparison | Compare DB event hash with on-chain transaction hash |
| Explorer link | External blockchain explorer URL | For independent verification |

### 4B. Implementation Tasks

**Task 4.1 — Build Blockchain Audit page (web)**
```
Location: website/src/pages/BlockchainAudit.jsx

Sections:

1. Chain Health Summary (top)
   - Total Events Anchored: count
   - Last Anchor Time: timestamp
   - Chain Sync Status: ✅ In Sync / ⚠️ Lagging / ❌ Out of Sync
   - Verification Pass Rate: percentage

2. Event Explorer Table
   - Filterable by event type, date range, entity, batch/product ID
   - Columns: Timestamp, Event Type, Entity, Batch/Product, Tx Hash, Status
   - Click any row → Event Detail (Task 4.2)

3. Verification Tool
   - Input: Batch ID, Product ID, or Transaction Hash
   - Output: Full event history with verification status
   - Cross-checks DB record against on-chain record
   - Shows ✅ MATCH or ❌ MISMATCH for each event

4. Smart Contract Status
